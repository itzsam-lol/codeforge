# CodeForge Sentinel

System-level proctoring companion app (Tauri v2 + Rust). See the implementation plan for the full phased scope; this README only covers what's actually built and how to run it.

## Status: Phases 1-7, 9, and 10 done (webcam/audio — Phase 8 — is handled in-browser by apps/web, not by this native app; see below). Phase 11 partially not possible (see below).

What exists right now:
- A working Tauri v2 project (`src-tauri/`) + Vite/React/TS frontend (`src/`), wired into the npm workspace as `@codeforge/sentinel`. Compiled, linked, and launched successfully — verified live via `cargo check`, `cargo clippy` (zero warnings), and repeated `npm run dev:sentinel` runs (a real "CodeForge Sentinel" window opens and stays responsive), including actual window screenshots to verify the UI, not just that it compiles.
- `get_system_info`: OS name/version/hostname, rendered on load (Phase 1).
- A background watchdog thread (`src-tauri/src/services/watchdog.rs`) polling every 3s for blacklisted processes across the spec's categories (remote desktop, VM tooling, screen sharing, AI assistants, screenshot tools, automation, communication apps). Critical categories are blocked on sight; everything else gets a 30s soft-block grace period before escalating. Also flags orphaned processes. Violations stream live to the frontend (`src/hooks/useProcessMonitor.ts`) and render in `SystemStatus`/`ViolationAlert` (Phase 2).
- `set_auto_terminate_on_hard_violation` exists but defaults **off** — auto-killing a candidate's process is an explicit opt-in, not a silent default.
- `detect_virtual_machine` (`src-tauri/src/commands/vm_detector.rs`, Phase 3): combines CPUID hypervisor signals, network MAC vendor prefixes, Windows registry BIOS/service checks, and filesystem artifacts into a 0-100 confidence score, deliberately weighted so Windows 11's Virtualization-Based Security and Hyper-V-backed WSL2/Docker Desktop don't false-positive a real physical dev machine — verified against this exact scenario live. Rendered in the `VmStatus` card.
- The UI is built on apps/web's actual design system, not a lookalike: same Tailwind v4 `@theme` tokens (`src/styles/globals.css`, kept in sync with `apps/web/src/app/globals.css`), same `Button`/`Card`/`Badge`/`Field`/`Input` primitives (`src/components/ui.tsx`, ported from `apps/web/src/components/ui.tsx`), same self-hosted Geist/Geist Mono fonts (via `@fontsource`, since this isn't Next.js so `next/font` isn't available), same 19px base type size and `cf-elevation`/`cf-grid-mesh` treatment.
- Root scripts: `npm run dev:sentinel` and `npm run typecheck` include this workspace.

Phases 4-6 added: `kiosk.rs` (fullscreen/always-on-top toggle + display count, and the real WH_KEYBOARD_LL global hotkey-block hook blocking Alt-Tab/Alt-Esc/Alt-F4/Win/PrintScreen system-wide — both now wired into the UI via `src/components/LockdownControl.tsx`'s "Start Lockdown"/"End Lockdown" flow, which sequences kiosk window + hotkey lock + clipboard lockdown + capture protection together. The hook's install/uninstall lifecycle is live-verified by `commands::kiosk::tests::hotkey_lock_installs_and_uninstalls_cleanly`, which actually installs and removes a real hook rather than just compiling; interactive in-app verification (does it really block Alt-Tab, does "End Lockdown" restore normal use) still needs a human at the keyboard — no desktop GUI automation tool was available to do that step here), `screen_guard.rs` (SetWindowDisplayAffinity capture protection — live-verified), `clipboard.rs` (polling-based clipboard guard + one-shot clear — compiled/clippy-clean, not live-tested against a real clipboard). Task Manager disabling (part of the original Phase 4 spec) was deliberately not built — a persistent registry security-policy change needs its own explicit go-ahead.

Also added since: `commands::input_injection_detector.rs` (kernel keyboard/mouse filter-driver + virtual-HID-device + loaded-module + remote-input-host-window detection, same composite-scoring shape as `vm_detector.rs`, rendered in the `InputInjectionStatus` card and polled every 5th watchdog tick), and `src/components/PracticeMode.tsx` (a no-server-Test, no-heartbeat self-check candidates can run before test day — same pre-flight checks and lockdown sequence as the real thing, clearly labeled as not recorded).

Phase 7 (`network_watcher.rs`): `get_active_connections` enumerates established TCP connections + owning process via `GetExtendedTcpTable`. No hardcoded allowlist/blocklist of IPs — that's fragile (shared CDN IPs, rotation). `flag_unexpected_connections` takes an allowlist as an argument instead.

Phase 9 (`integrity.rs`): `get_system_fingerprint` hashes CPU/RAM/display/MAC/OS/hostname/disk-serial into one SHA-256. GPU model omitted (needs DXGI/WMI, sysinfo doesn't expose it). Drift-detection polling and cross-session server matching are Phase 10/dashboard work, not built.

Phase 10, now fully done: `POST /api/candidate/sentinel-heartbeat` (apps/api) + a 30s sweep flagging stale heartbeats (`sentinel_heartbeat_lost`) + this app's `services/heartbeat.rs` client, all live-verified end-to-end against a real running instance (heartbeat → DB → violation events → integrity recalculation → sweep → auto-flag, not just typechecked). On top of that:
- `requireSentinel` test setting (`packages/shared`'s `testSettingsSchema`) gates `/api/candidate/start` and is surfaced to the candidate as `proctoring.sentinelRequired` on `GET /api/candidate/context`, alongside a `session.sentinelConnected` flag (a heartbeat within the last `HEARTBEAT_TIMEOUT_MS`, same 60s window the stale-sweep uses).
- `apps/web`'s `/t/[token]` page gates `StartCard` behind a new `SentinelGate` component when `sentinelRequired` is true and not yet connected — it opens a `codeforge-sentinel://start?apiUrl=...&token=...` link and polls context every 3s until connected, with a fallback download link to `GET /downloads/sentinel-setup` (apps/api, streams the installer from the existing S3/MinIO bucket — see that route's own comment) for anyone who doesn't have Sentinel yet. The primary path is the onboarding email sent when a Sentinel-required test invite goes out (`sendSentinelOnboardingEmail`, apps/api/src/lib/email.ts) — it covers the download link, install instructions, and a warning to test before test day.
- `codeforge-sentinel://` deep-link protocol registration (`tauri-plugin-deep-link`, configured in `tauri.conf.json`'s `plugins.deep-link.desktop.schemes`), paired with `tauri-plugin-single-instance` (the `deep-link` feature) so a candidate clicking the link while Sentinel is already open reuses the window instead of spawning a duplicate. `src-tauri/src/services/session_link.rs` parses the URL, starts the heartbeat loop, and emits `sentinel://session` for the new `SessionConnect` card (`src/components/SessionConnect.tsx`) to show connected/waiting/error state — with a manual API-URL/token fallback for when the link can't reach Sentinel. Self-registers the protocol on every dev launch (per-user registry write, no admin rights) so this works under `npm run dev:sentinel` too, not just an installed build.
- Live-verified end-to-end against the real API + Postgres: a real invitation token, a real `codeforge-sentinel://` link opened via `Start-Process`, confirmed single-instance forwarding (no duplicate window), and `GET /api/candidate/context` flipping `sentinelConnected` to `true` off a real heartbeat POST — not just typechecked.

**Phase 8 (webcam/audio): not part of this app.** It's built in `apps/web` instead — `useWebcamCapture`/`captureSnapshot` in `apps/web/src/lib/proctoring.ts`, wired into `EnvCheck` (identity photo) and `TestRunner` (random-interval snapshots) — since the candidate is already in the browser for the timed test itself; a second native capture path would be redundant. Sentinel's own scope stays system-level monitoring (processes, network, VM/integrity, kiosk, clipboard).

**Phase 11 (security hardening), partial**: real branding (icons generated from CodeForge's actual mark via `tauri icon`, `tauri.conf.json`'s `bundle` block filled in with publisher/copyright/descriptions and a `perMachine` NSIS installer config) and a hosted, downloadable installer now exist — `npm run build` in `apps/sentinel` produces `src-tauri/target/release/bundle/nsis/CodeForge Sentinel_<version>_x64-setup.exe`, uploaded manually to the S3/MinIO bucket at `sentinel/CodeForge-Sentinel-Setup.exe` and served by `GET /downloads/sentinel-setup`. Still not done, and can't fully be by an agent: code signing (EV certificate, Apple Developer ID + notarization) and a real auto-update server both require you to own actual paid certificates/accounts — the installer ships unsigned, so Windows SmartScreen shows an "unknown publisher" warning candidates click through. The self-hash anti-tamper check is the one remaining piece that's genuinely buildable without external resources; not attempted yet.

Also not implemented: the spec's real-time process-spawn detection (Phase 2, Windows WMI/macOS Endpoint Security/Linux netlink) and VM-detection timing-attack signal (Phase 3, explicitly "supplementary, not primary" in the spec).

**Deliberate deviations from the spec, worth knowing about:**
1. `tauri.conf.json`'s window still launches as a normal decorated, resizable, non-always-on-top window — it only becomes the fullscreen/borderless/always-on-top kiosk window at runtime, once "Start Lockdown" (`LockdownControl.tsx`) is clicked, with "End Lockdown" always reachable inside that locked-down view to reverse it. Launching directly into an inescapable fullscreen window from `tauri.conf.json` itself was deliberately avoided — anyone running `npm run dev:sentinel` would be stranded before ever seeing the pre-flight checks.

## Before production

Fixed this pass (both were flagged in an earlier critical-review pass and left open until now — see git history for the review itself):
- `network_watcher.rs`'s `read_tcp_table()` cast a `Vec<u8>` buffer to a `MIB_TCPTABLE_OWNER_PID*` — technically unsound (that struct needs 4-byte alignment, `Vec<u8>` only guarantees 1-byte), harmless in practice on x86_64 but not something to leave in place. Now backed by `Vec<u32>`, which actually guarantees the alignment the cast needs.
- `install_hotkey_lock`'s "already installed?" check and the store that claims the slot were two separate non-atomic steps — two concurrent calls could both pass the check, install two hooks, and leak one (its thread ID lost, unable to ever be uninstalled). Now a single `compare_exchange`. Low real-world severity since this command isn't wired to any UI yet, but cheap to close correctly rather than leave as a known bug.

**Still open, not attempted this pass:**
- **The candidate token travels as a `codeforge-sentinel://start?...&token=...` URL, which becomes a literal OS command-line argument** (`"codeforge-sentinel.exe" "codeforge-sentinel://...&token=RAWTOKEN"`) for as long as Sentinel's process is alive — visible to anything else running locally with permission to read another process's command line (Task Manager's "Command line" column, Process Explorer, WMI, command-line process-creation auditing if enabled). The token only ever authorizes actions on the candidate's own session (heartbeats, nothing else), and it's the same token already sitting in the browser tab's memory, so this isn't a *new* secret exposure so much as an extension of an existing one to local process listings too — but it's still worth closing properly with a short-lived, Sentinel-only token (the browser exchanges the long-lived candidate token for one with a few minutes' TTL right before building the link, instead of handing over the real one) rather than accepted as-is. Not built — needs a new backend endpoint and a decision about where that token type lives in the auth model, more than a quick patch.
- **The client-trust gap**: nothing stops a candidate from POSTing fake heartbeats directly to `/api/candidate/sentinel-heartbeat` without ever running Sentinel, since the only credential required is the same `x-candidate-token` the browser already has. Closing this for real needs signed/attested telemetry (e.g., Sentinel signs each heartbeat with a key that isn't just sitting in the request the candidate's own browser could replay) — genuine infrastructure work, not something to bolt on without designing it properly.
- **Phase 11**: code signing (EV certificate, Apple Developer ID + notarization) and a real auto-update server both require paid certificates/accounts only you can provide — not buildable by an agent. The self-hash anti-tamper check is the one piece that's technically buildable without external resources, but was deliberately skipped: without a trusted baseline hash to compare against (infrastructure that doesn't exist yet), it would just be theater, not real anti-tamper protection.
- **Interactive lockdown verification**: the hotkey hook's install/uninstall lifecycle is live-tested (see above), but nothing in this environment could press Alt-Tab/Win/Alt-F4 and observe the OS actually blocking it, or click "Start Lockdown"/"End Lockdown" in the running app — that step needs a human at the keyboard, ideally once per machine class you deploy to (this dev machine's real hardware, then again on whatever Windows image test-takers will actually run).

## Setup

Requires:
1. **Rust** via [rustup](https://rustup.rs) (Windows: `winget install Rustlang.Rustup`).
2. **MSVC Build Tools** (Windows only) — the "Desktop development with C++" workload. Silent install: `winget install --id Microsoft.VisualStudio.2022.BuildTools --override "--wait --passive --add Microsoft.VisualStudio.Workload.VCTools --includeRecommended"`. Rust alone can't link anything on Windows without this.
3. **WebView2**: pre-installed on Windows 11 / most Windows 10 systems.

```sh
npm install          # from the repo root, if not already done
npm run dev:sentinel  # from the repo root — builds the Rust backend + starts Vite, opens the app window
```

**If you're on Git Bash and hit a linker error like `link: extra operand '...'`**: that's Git's own `/usr/bin/link.exe` (a hardlink utility) shadowing the real MSVC linker on PATH. Run `cargo`/`npm run dev:sentinel` from PowerShell or cmd instead, not Git Bash.

The first build compiles ~378 crates from scratch and is slow; subsequent runs are incremental (~1s once nothing changed). If a build fails with a `The process cannot access the file because it is being used by another process` error on an intermediate `.o` file, that's a transient Windows file-lock (commonly antivirus real-time scanning) — just retry.
